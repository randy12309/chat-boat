Plan Assistant

How the system is built: an LLM supervisor, three specialist agents (policy, account, payment), seven MCP tools, three data stores

Plan Assistant answers a plan member’s questions about premiums, eligibility and policy, and lets them pay an outstanding premium. A member signs in, chats, and sees two live cards above the conversation: what is due, and what is unread.Everything here describes the code in this repository, branch feature/pgvector-faq-policy. Nothing is hard-coded: amounts, thresholds, policy text and FAQ answers all come from a database.

There are five moving parts: an Angular 22 browser app, a FastAPI backend that runs one LangGraph graph of four agents, a FastMCP tool server, MySQL for member data and Qdrant (the qdrant/qdrant vector database) for knowledge.

The whole picture

How many agents?

Four agents in one LangGraph graph (backend/app/agents/graph.py): an LLM supervisor and three specialists. Each one that talks to the customer is an LLM agent; there is no separate writer and no catch-all general agent.The supervisor is a model call, not a keyword router. It answers greetings and general insurance knowledge itself (direct). No keyword rules exist anywhere: if the model is off or unreachable, the user is told the assistant is temporarily unavailable instead of getting a guess.

How the agent connects

  1. The browser signs in at /api/v1/auth/login and receives a JWT valid for one hour.
  2. It posts the question to /api/v1/chat/stream. The backend replies with server-sent events: delta chunks, then a done event carrying sources and any UI hint.
  3. The graph runs. The supervisor model picks a specialist; that agent (or its tool loop) opens an HTTP session to MCP_SERVER_URL (http://127.0.0.1:8765/mcp) and calls a tool with the signed principal.
  4. The MCP server verifies the principal, queries MySQL or Qdrant, and returns JSON tagged with its source.
  5. The answer is saved to the chat and the conversation memory.

If the MCP server is down, the tools fail, which is the cause of the original “eligibility is not fetching” bug. start.ps1 now starts it first.

Hierarchical agents and their MCP connections

The graph is a two-level hierarchy. One supervisor sits on top and holds no data tools; it only decides who works. Three specialist agents sit below it and are the only parts that reach data. Read the picture top to bottom: the supervisor delegates, each agent uses its own path, and only the paths marked MCP go through the tool server.The hierarchy is shallow by design: one supervisor over leaf agents. A mixed question starts the policy and account agents in the same step.

Swimlane: a question that needs policy and account data

“When will I be eligible for pension and insurance, and what happens if I pay late?” The supervisor model picks policy_and_account. The policy and account agents then run in the same step, in parallel, each calling the model for its own part; a join step stitches the two answers. The payment path

The payment agent calls get_due_payments over MCP. If nothing is due it says so and shows no card; otherwise it asks “Is that right?” and the browser shows Yes / No, then the pay card. No model decides whether money moves: the card posts to POST /api/v1/payments/pay with the member’s own unpaid ids and an authorization tick. A typed confirm or cancel for an already prepared quote is an exact-match gate that skips the supervisor model.

How the agents use the model

  • Supervisor. One short Groq call (temperature 0, tool choice forced) to a single route_request tool. It chooses policy, account, policy_and_account, payment or direct, and writes the reply itself only for direct. If the call fails twice, the user gets a "temporarily unavailable" reply; there is no keyword fallback.
  • Policy agent. Retrieval-augmented: cache / Qdrant / MCP give it the policy text, and a streamed Groq call turns that text into a clear answer. Nothing found means it says so without calling the model.
  • Account agent. A streamed Groq tool-calling loop. The model decides which MCP tools to call; results go back to it as tool messages; it then explains them.
  • Payment agent. Plain code; no model.

How MCP is connected

  • Transport. The MCP server is a separate process, started with python -m mcp_server.server, serving streamable HTTP at http://127.0.0.1:8765/mcp. The backend finds it through MCP_SERVER_URL.
  • Client. backend/app/agents/mcp_client.py opens a fastmcp client session and calls an allow-listed tool by name.
  • Identity. The model never supplies a username. The backend adds a signed principal for the logged-in user, and the MCP server rejects any call whose principal does not verify.
  • Money. No model can bind a payment tool. The payment agent reads due items; the pay card charges through the authenticated backend endpoint.

Where the embeddings live

Embeddings are made by fastembed with the model sentence-transformers/all-MiniLM-L6-v2, 384 dimensions, running locally on the CPU. No text is sent to a third party for embedding.The first lookup after a restart takes about five seconds while the model loads. This is the main part of the slow first token.

They are stored in Qdrant (the qdrant/qdrant Docker image, or its embedded mode for tests) as the collections plan_settings, policy_topics, faq_entries, faq_learned and sag_aftra_knowledge. The last one holds the SAG-AFTRA policy reference PDF parsed into 27 policy records (parents) and 300 question records (children), each with its answer mode, related policy IDs and source links. Vector collections use 384-dimension cosine distance.

The cache

An in-memory cache sits in front of the database. It holds the most frequently asked public questions (ranked by hit_count), rephrasings asked at least FAQ_PROMOTE_MIN_HITS times, and recent matches with a time-to-live. The lookup order is: cache, exact match in faq_entries, Qdrant similarity. Every answered question increments its count, so after a restart the cache is rebuilt from real usage. Only public answers are cached; nothing about a member is.

Production architecture

This is the target design, not what runs today. The code already separates the pieces correctly; production mostly swaps each single local process for a managed, replicated service and moves every piece of in-process state into a shared store.Product names are examples. Any managed MySQL, Qdrant Cloud or a self-hosted Qdrant cluster, and Valkey-compatible service fits.

Things to fix before going live

  • In-process state. The MCP server keeps its prepared quotes and a paid-set in memory, and the backend keeps the FAQ cache in memory. With more than one replica these disagree. Move them to Redis or MySQL, or delete them: no agent uses quote_payment / execute_payment any more, so those two tools can be removed.
  • Payments are the only write that moves money. Keep them out of the model path. The pay card calls an authenticated endpoint that takes the caller’s own unpaid ids and an idempotency key; keep that, add the provider’s webhook for the final status, and audit-log every attempt.
  • Backups and failover. Both databases need automated backups and a tested restore. The vector tables are rebuildable from source text, the MySQL tables are not.
  • Prompt-injection limits. Policy text and member messages are untrusted input to the model. Agents only read through allow-listed tools and cannot change data, which is what keeps this safe; keep it that way as tools are added.
  • Cost and abuse. Rate-limit chat per user and cap output length, since each turn costs a supervisor call plus an agent call.

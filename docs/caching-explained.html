How Caching Works in Plan Assistant

A guided tour of the Valkey cache for policy answers and per-user account data

Plan Assistant answers two kinds of questions. Policy questions have the same answer for everyone. Account questions (balance, due payment, eligibility) belong to one person. The cache treats the two kinds very differently, and this document explains how, why, and with which settings.

1. The big picture

A cache is a fast, temporary copy of an answer. Reading from the database, calling MCP tools and asking the LLM are all slow and costly. The cache lets the app skip those steps when it already knows the answer.

The system uses one Valkey server (Valkey is an open-source Redis-compatible in-memory store) and two separate cache families:

FamilyWho sees itWhat it holds
Policy cacheShared by all usersPublic FAQ and policy answers with their question embeddings
Account cachePrivate to one userBalance, eligibility, due payments, account record, premium breakdown, payment methods, payment history, and LLM-written answers
Policy text is public and identical for every member, so sharing it is safe and saves memory. Account data is personal, so every key is derived from the user.

The main rule is identity comes from the server. The user is identified by the authenticated session, never by the text of the question or a value the LLM supplies.

2. Architecture

A chat message goes through the backend, which routes it to the policy agent or the account agent. Each agent checks Valkey before doing slow work.

Policy lookup order

  1. Exact match in Valkey (the question is normalized, then hashed).
  2. Per-worker memory: a small hot cache of the most recent questions.
  3. Semantic match: compare the question's embedding with stored ones, accept at or above 0.9 similarity.
  4. Miss: use Qdrant and MCP policy retrieval, ask the LLM, then store the result.

Account lookup order

  1. Authenticate the user and read the user's own answer entries.
  2. Exact question match among that user's entries.
  3. Semantic match, only for simple balance questions, only among that user's own entries, and only when similarity is strictly above 0.85.
  4. Miss: the account agent calls MCP tools. Each tool reads through its own per-user cache first, then the database.
  5. The LLM writes the answer from the tool result. If every tool call succeeded, the answer is saved to that user's cache.
A brand-new user takes the miss path on the first question. There is no pre-creation step; the user's cache appears when the first answer is stored.

5. Important variables and keys

User hash
SHA-256 of the username. Every account key contains it, so raw names are not stored in key names.
Generation token
A random value stored per user. A reader remembers it before reading the database, and writes to the cache only if it has not changed. This stops a stale read that was running during a payment from being saved.
Account keys
plan:account:{hash}:generation, :balance, :eligibility, :due, :account, :premium. The braces keep one user's keys together on one server slot so a script can change them atomically.
Answer hash
plan:account:answer:{hash}: a hash holding the user's saved answers, each with question, answer, sources, embedding and expiry.
User LRU list
plan:account:answers:users: a sorted set of users by last use. Its size is the active-user limit.
Policy keys
plan:faq:{hash} for the exact answer, plan:faq:sem:{hash} for question plus embedding plus answer.
Payment methods and history keys
plan:account:HASH:payment_methods and plan:account:HASH:payments:STATUS:LIMIT (no braces, so these are separate from the tool keys above but are still deleted by the payment invalidation).

6. How the cache is updated

EventWhat happens
First question by a new userMiss, MCP read, LLM answer, store tool data and answer for that user.
Repeat questionHit. Reading also marks the user as recently used.
Different questionOnly the data that question needs is loaded and stored. Nothing is preloaded.
Time passesEntries expire by TTL and reload on the next question.
User paysAll of that user's cached account data and saved answers are deleted. Other users are untouched. The next question reloads fresh data.
Payment during an answer in progressThe generation token changed, so the stale answer is rejected, not stored.
Fifth user (limit 4)The least recently used user's saved answers are removed. That user is still served normally.
Tool failure or not-foundNever cached.
Valkey down or slowThe cache is skipped and the app reads from the source. The answer is still correct, only slower.
Policy learnedStored with exact and embedding keys for 1 hour. Policy can also be bulk-loaded from Excel.
Change made outside the appNot detected. The old value can live until the TTL ends (up to 120 s for account data).

The cache is never the source of truth. MySQL is. The cache is a disposable copy whose worst case is a few seconds of stale data.

7. Caching terminology

Cache hit / miss
Hit: the answer was found in the cache. Miss: it was not, so the slow path runs.
Hit rate
Hits divided by total lookups. Higher means less load on MCP, MySQL and the LLM.
TTL (time to live)
How long an entry may live before it expires automatically.
Invalidation
Deleting or marking entries as outdated because the underlying data changed.
Stale data
A cached value that no longer matches the source.
Cache-aside (lazy loading)
The app checks the cache, and on a miss loads from the source and stores it. This is the pattern used here.
Cache warming
Filling the cache before users ask. Used for policy FAQ imports.
Cold start / cold cache
An empty cache, for example after a restart. All requests miss at first.
Cache stampede
Many simultaneous misses for the same data all hitting the source at once.
Request coalescing
Letting identical simultaneous misses share one source call. Not yet implemented here.
Eviction
Removing entries to make room. Here either by the user limit (LRU) or by Valkey when memory is full (LFU).
LRU (least recently used)
Evict the entry unused for the longest time. Used for the active-user limit.
LFU (least frequently used)
Evict the entry used least often. Used by Valkey's memory policy.
Exact cache
Matches only when the normalized question is identical.
Semantic cache
Matches questions with similar meaning, using embeddings.
Embedding
A list of numbers representing the meaning of a sentence.
Cosine similarity
A score from -1 to 1 comparing two embeddings. Higher means closer in meaning. Thresholds here: 0.85 (account) and 0.9 (policy).
Threshold
The score that must be passed before a semantic match is trusted.
False hit
A semantic match that has a similar score but a different meaning, for example "balance" versus "due date". The reason account semantic matching is limited to simple balance questions.
Namespace / key prefix
A naming convention such as plan:account: that separates kinds of data.
Hash tag
The braces in a key. Only the text inside decides which cluster slot a key uses.
Generation token / versioning
A value that changes on invalidation so old in-flight writes can be rejected.
Race condition
Two operations overlapping, such as a read and a payment, producing a wrong result.
Lua script (atomic operation)
A small script run inside Valkey that executes as one uninterruptible step.
Tenant isolation
One user can never read another user's cached data.
Graceful degradation / fail-open
If the cache fails, the app keeps working using the source.
Hot cache
A small in-process memory layer for the most recent items.
Source of truth
The authoritative store: MySQL.

8. Scale: 90k users, 20k concurrent, 10k active

  • Registered users: 90,000. Most are idle. Idle users cost no cache memory because the cache is lazy.
  • Concurrent: 20,000. Each worker needs fast Valkey calls with short timeouts so that a slow cache never blocks chat.
  • Active: 10,000. This maps to ACCOUNT_CACHE_MAX_USERS=10000 in production. Development uses 4 to make eviction easy to test.
  • Memory estimate: users × answers per user × bytes per entry, plus embeddings and overhead. Measure it before raising the limit.
  • Cold start risk: after a restart many users miss at once. Request coalescing or warming the most active users would soften this.
  • These are planning numbers, not proven capacity. A load test is still required.

9. Limitations to mention honestly

  • Changes made outside the app do not clear the cache; the TTL is the safety net.
  • Account semantic matching covers only simple balance questions. Other questions need an exact match.
  • The policy semantic scan reads up to 2,000 entries, which will not scale indefinitely. A vector index would replace it.
  • The user limit applies to saved answers only. Tool-level data caches are bounded by TTL and the Valkey memory limit.
  • One development Valkey with no persistence and no high availability is not a production topology.
  • The multi-key atomic scripts assume a single Valkey node or keys on the same slot.
